## 1. 设计原则与约束

### 1.1 核心功能保持不变

**重要约束**: 
- ✅ 程序核心功能：**读取 `.key` 文件 → 输出 Markdown 文档**
- ✅ 保持现有输出格式：
  - `*_docs.md` - 详细参考文档
  - `*_overview.md` - 工程概览
  - `ls_dyna_md/docs/SUPPORTED_COMMANDS.md` - 支持的关键字列表（自动生成）
  - `*_AI_REQ.md` - 未识别关键字的实现需求（如有）
- ✅ 保持增量构建机制
- ✅ 保持批量处理能力

**GUI 的作用**:
- 🎯 提供可视化的文件管理界面
- 🎯 简化批量处理操作
- 🎯 提供实时处理进度反馈
- 🎯 方便查看和对比生成的文档
- 🎯 **不改变核心解析逻辑和输出格式**

---

### 1.1.1 Key 文件的实际情况

**重要认识**: 在实际工程中，很多 `.key` 文件只是车辆一部分组件的模型，并不包含完整的仿真设置。

**常见情况**:
- ✅ **包含**: 网格数据（节点、单元）、部件定义、材料定义、截面定义、接触定义
- ❌ **可能不包含**: 
  - 边界条件（`*BOUNDARY_*`, `*LOAD_*`）
  - 求解器设定（`*CONTROL_*` 系列）
  - 材料详细信息（某些材料模型可能只有基本参数）
  - 控制卡片（`*CONTROL_*`）
  - 输出设置（`*DATABASE_*`）

**设计原则**:
1. **空内容不显示**: 如果某个类别的内容为空，在 `*_docs.md` 中不显示该章节
2. **检查清单展示**: 在 `*_overview.md` 中必须显示检查清单，用对勾（✓）表示包含，空白表示不包含
3. **分类展示**: 由于命令非常多，检查清单应该按类别分组展示（如：控制卡片、边界条件、材料、接触等）
4. **GUI 同步显示**: GUI 界面应该显示与 overview 文档相同的检查清单效果，方便快速了解模型包含的内容

---

### 1.2 关键字扩展计划

**当前状态**: 程序已支持 20+ 种关键字类别

**扩展目标**: 作为 LS-Dyna 专家，整理整车碰撞模型中涉及的所有常用关键字，并逐步整合到程序中。

**扩展策略**:
1. **保持现有机制**: 
   - 程序自动生成 `SUPPORTED_COMMANDS.md`（能力矩阵）
   - 程序自动生成 `*_AI_REQ.md`（未识别关键字的需求文档）
2. **渐进式扩展**: 
   - 先扩展最常用的关键字（见 2.1 节）
   - 通过实际使用中遇到的未识别关键字逐步完善
3. **向后兼容**: 
   - 新关键字不影响现有功能
   - 保持现有数据结构扩展性

---

### 1.3 GUI 设计原则

1. **简洁高效**: 界面简洁，操作直观，减少学习成本
2. **信息层次**: 重要信息突出显示，次要信息可折叠
3. **批量友好**: 针对整车模型（多子模型）场景优化
4. **文档导向**: GUI 主要用于管理文件和查看文档，不替代文档本身
5. **轻量级**: 不引入复杂的数据存储，保持程序轻量

## 2. 文档生成逻辑与 Overview 设计

### 2.1 MD 文档生成原则

#### 2.1.1 详细文档（`*_docs.md`）生成逻辑

**核心原则**: **空内容不显示**

- ✅ **有内容则显示**: 如果解析到某个类别的数据，在文档中显示该章节
- ❌ **无内容则跳过**: 如果某个类别为空（如没有边界条件、没有控制卡片），则不在文档中显示该章节
- 📝 **章节顺序**: 按照重要性排序，有内容的章节优先显示

**示例**:
```
如果 key 文件包含：
- ✓ 节点、单元数据
- ✓ 材料定义
- ✓ 接触定义
- ✗ 边界条件（无）
- ✗ 控制卡片（无）

则 *_docs.md 中显示：
1. 基本信息（节点、单元统计）
2. 材料定义
3. 接触定义
（不显示边界条件和控制卡片章节）
```

### 2.2 Overview 文档（`*_overview.md`）设计

#### 2.2.1 检查清单设计原则

**核心功能**: Overview 文档必须包含一个**完整的检查清单**，展示该 key 文件包含和不包含的内容。

**设计要点**:
1. **必须显示所有类别**: 即使某个类别为空，也要在检查清单中显示（用空白表示不包含）
2. **分类展示**: 由于命令非常多，必须按类别分组展示
3. **对勾标识**: 包含的内容用 ✓ 表示，不包含的用空白或 ✗ 表示
4. **层次清晰**: 大类下可以有小类，便于快速定位

## 3. 关键字扩展计划

### 3.1 整车碰撞模型常用关键字清单

基于 LS-Dyna 整车碰撞仿真经验，以下是应该优先支持的关键字（按重要性排序）：

#### 3.1.1 控制卡片（CONTROL 系列）⭐⭐⭐⭐⭐

**最高优先级** - 控制求解器行为，影响计算精度和稳定性

| 关键字 | 功能 | 关键参数 |
|--------|------|----------|
| `*CONTROL_TERMINATION` | 计算终止条件 | ENDTIM, DTMIN, ERODE |
| `*CONTROL_TIMESTEP` | 时间步长控制 | DT2MS, TSSFAC, ISDO |
| `*CONTROL_HOURGLASS` | 沙漏控制 | IHQ, QH, QM |
| `*CONTROL_ENERGY` | 能量控制 | HGEN, RWEN, SLNTEN |
| `*CONTROL_BULK_VISCOSITY` | 体积粘性 | Q1, Q2 |
| `*CONTROL_CONTACT` | 接触控制 | SLSFAC, RWPNAL, IGNORE |
| `*CONTROL_SOLUTION` | 求解器选项 | SOLN, NLQ |
| `*CONTROL_ACCURACY` | 精度控制 | INN, PID |
| `*CONTROL_IMPLICIT_*` | 隐式求解控制 | （如使用隐式） |
| `*CONTROL_OUTPUT` | 输出控制 | NPOPT, ECHO |

### 2.1 控制卡片（CONTROL 关键字） ⭐⭐⭐⭐⭐

**重要性**: 极高 - 控制求解器行为，影响计算精度和稳定性

**缺失内容**:
- `*CONTROL_TERMINATION`: 计算终止时间、能量检查
- `*CONTROL_TIMESTEP`: 时间步长控制（DT2MS、TSSFAC等）
- `*CONTROL_HOURGLASS`: 沙漏控制（IHQ、QH等）
- `*CONTROL_ENERGY`: 能量控制（HGEN、RWEN、SLNTEN等）
- `*CONTROL_BULK_VISCOSITY`: 体积粘性系数（Q1、Q2）
- `*CONTROL_CONTACT`: 接触控制（SLSFAC、RWPNAL等）
- `*CONTROL_SOLUTION`: 求解器选项（SOLN、NLQ等）
- `*CONTROL_ACCURACY`: 精度控制（INN、PID等）

**提取建议**:
```python
self.control_cards = {
    "TERMINATION": {"ENDTIM": value, "DTMIN": value, ...},
    "TIMESTEP": {"DT2MS": value, "TSSFAC": value, ...},
    "HOURGLASS": {"IHQ": value, "QH": value, ...},
    # ... 更多控制卡片
```

**GUI 展示需求**: 
- 在概览页面显示关键控制参数
- 提供参数合理性检查（如时间步长是否过小/过大）
- 对比不同子模型的控制参数差异

### 2.2 边界条件（BOUNDARY 关键字） ⭐⭐⭐⭐⭐

**重要性**: 极高 - 定义模型的约束和载荷边界

**缺失内容**:
- `*BOUNDARY_PRESCRIBED_MOTION_*`: 强制位移/速度/加速度
- `*BOUNDARY_SPC_*`: 单点约束（固定、滑动等）
- `*BOUNDARY_SPC_SET`: 集合约束
- `*LOAD_*`: 载荷定义（节点力、压力等）
- `*LOAD_BODY_*`: 体积力（重力、加速度等）

**提取建议**:

## 4. 技术选型建议

### 4.1 GUI 框架选择

**推荐方案**: **tkinter** (Python 标准库)

**理由**:
1. **零依赖**: Python 标准库，无需安装额外包
2. **轻量级**: 符合程序"保持简单"的设计原则
3. **功能足够**: 对于文件管理和进度显示，tkinter 功能足够
4. **跨平台**: Windows/Linux/Mac 都支持
5. **学习成本低**: 简单易用

**备选方案**: **PyQt6**
- 如果未来需要更复杂的界面功能，可考虑迁移
- 当前阶段建议先用 tkinter 实现 MVP

---

### 4.2 数据存储

**方案**: **不引入数据存储**

**理由**:
- 程序核心功能是"读取 key 文件 → 输出 MD 文档"
- 不需要存储解析结果，直接读取生成的 MD 文档即可
- 保持程序轻量，避免复杂性

**如果需要缓存**:
- 可以简单记录文件处理状态（JSON 文件）
- 记录：文件名、处理时间、输出文件路径
- 用于增量构建判断

---

### 4.3 多线程处理

**推荐**: 使用 `concurrent.futures.ThreadPoolExecutor`

**实现要点**:
- GUI 主线程负责界面更新
- 工作线程负责文件解析
- 使用队列传递进度信息
- 避免阻塞 GUI

---

### 4.4 文档查看

**方案**: 使用系统默认程序打开 MD 文件

- Windows: 使用默认 Markdown 查看器（如 Typora、VS Code）
- 或集成简单的 Markdown 预览组件（如 `markdown` + `html` 预览）
- 优先使用外部程序，保持 GUI 轻量

## 7. 总结

### 7.1 核心设计要点

1. **Key 文件实际情况认识**:
   - 很多 key 文件只是车辆一部分组件的模型
   - 可能不包含边界条件、求解器设定、材料详细信息、控制卡片等
   - 程序必须能够正确处理这种情况

2. **MD 文档生成逻辑**:
   - **空内容不显示**: 如果某个类别为空，在 `*_docs.md` 中不显示该章节
   - **检查清单必须显示**: 在 `*_overview.md` 中必须显示完整的检查清单
   - **分类展示**: 命令非常多，必须按类别分组展示（9大类）

3. **Overview 文档设计**:
   - 必须包含完整的检查清单
   - 用 ✓ 表示包含，用空白或 ✗ 表示不包含
   - 可以显示数量统计（如 "5个"）
   - 按重要性分为9大类：控制与求解器、边界条件与载荷、材料、接触、网格、截面、连接、输出、其他

4. **GUI 界面设计**:
   - **必须显示检查清单**: GUI 界面应该显示与 overview 文档相同的检查清单效果
   - **内容概览优先**: 检查清单视图应该是默认显示的第一个标签页
   - **空标签页不显示**: 如果某个类别为空，对应的详细标签页不显示，但在检查清单中仍然显示（标记为不包含）
   - **快速判断**: 用户可以通过检查清单快速判断模型包含和不包含的内容

5. **关键字扩展**:
   - 保持现有机制（自动生成能力矩阵和需求文档）
   - 渐进式扩展，不影响现有功能
   - 扩展的关键字需要整合到检查清单分类体系中

### 7.2 实施优先级

**Phase 1: 核心功能实现**
1. 实现检查清单生成逻辑（overview 文档）
2. 实现空内容不显示逻辑（docs 文档）
3. 实现检查清单分类体系（9大类）

**Phase 2: GUI 基础功能**
1. 实现检查清单视图（GUI）
2. 实现文件选择和批量处理
3. 实现文档查看功能

**Phase 3: 功能增强**
1. 关键字扩展（按计划逐步添加）
2. GUI 功能增强（对比视图、统计图表等）
